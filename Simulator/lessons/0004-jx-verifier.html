Lesson 4

The Bytecode Verifier

How jx.verifier proves a class is safe to run natively — before armOS ever executes it

src/jx/verifier/ → entry point Verifier.java

Why armOS needs a verifier

The four simulators you've studied so far interpret instructions at runtime. The JVM in this codebase does something different: it takes Java bytecode and — following the JX OS model — prepares it to run as native code in supervisor context. There is no OS underneath to catch a type error with a segfault; type safety is the security boundary. Untrusted programs must be proven safe statically, before execution.

That proof is the job of jx.verifier. If you ever add a new opcode to the JVM, this package is what decides which bytecode is allowed to reach your interpreter. It is the gatekeeper.

The engine: abstract interpretation

All four analyses share one workhorse: MethodVerifier. It treats each method as a control-flow graph and simulates it using abstract values instead of concrete ones — this is abstract interpretation.

The pipeline inside MethodVerifier:

Parse

new BCLinkList(method, cPool) (MethodVerifier.java:64) turns the raw bytes into a doubly-linked list of ByteCode objects. Opcodes with operands get specialized subclasses — BCBranch, BCMultiBranch, BCCPArgOp (constant-pool operands), BCWideOp (ByteCode.java:135). Each node links its targets and sources (ByteCode.java:200) — the CFG edges.

Seed

runChecks() (MethodVerifier.java:91) stamps the first bytecode with a copy of the initial abstract state (operand stack + local vars derived from the method signature), registers all JSR subroutines, then pushes it onto the worklist.

Iterate to fixed point

continueChecks() (MethodVerifier.java:118) pops bytecodes off the LIFO check queue. Each pop simulates one instruction's effect on its beforeState — the abstract state flowing into that bytecode. The resulting states are merged into each successor's beforeState. If the merge changed a successor, that successor is re-queued and re-analyzed. The queue drains only when every state has stabilized — a fixed-point computation.

The LIFO order is deliberate: it finishes one control-flow branch before starting another, which keeps JSR subroutine verification from running twice (MethodVerifier.java:115).

What a "simulation" does

The heart of the engine is JVMState.executeNextBC() (JVMState.java:71). In order it:

  1. Copies the state — analyses are purely static, they never mutate shared state.
  2. Handles JSR — if the next bytecode is JSR/JSR_W, the subroutine is verified separately and its result state merged into all RET targets (JVMState.java:85).
  3. Simulates exceptions — for each exception handler protecting this bytecode, it computes the state you'd land in if the instruction threw: stack cleared, exception object pushed, nextBC = handler (JVMState.java:93, TCState.java:25).
  4. Simulates the instruction via doExecuteNextBC() — the analysis-specific part (for TypeCheck this is BCStackEffect.simulateBC, a 1,100-line table-driven switch over all opcodes, TCState.java:18).
  5. Merges the result states into successors and re-queues any whose state changed (JVMState.java:114).

The merge operator — where safety is decided

Verification is a dataflow analysis, and merge is its "join" operation. When two control-flow paths meet at a bytecode, their abstract states must be combined:

// JVMState.java:174 — the join is stack ∧ locals
retval = stack.merge(mergeState.getStack())
       | lVars.merge(mergeState.getlVars());

The rules encode the JVM's type discipline:

  • Stack depth must agree. If two paths arrive with different operand-stack sizes, that's a VerifyException — "Stacks of different size" (JVMOPStack.java:124). This is the classic "merged stack heights must match" rule.
  • Types merge upward. Two different object types merge to their first common superclass, or T_OBJECT (java/lang/Object) if there is none (TCObjectTypes.java:239).
  • null merges into anything — the null type is compatible with every object type (TCObjectTypes.java:232).
  • Return true if anything changed — the signal that re-analysis is needed. This is what makes the worklist loop terminate with a precise, safe answer.
Why re-verify on change?

Suppose an if merges Object into a path that had String. The successor's locals are now less precise. That less-precise state could change the outcome of instructions after the merge point — e.g. a CHECKCAST or an INVOKEVIRTUAL. So every affected successor must be re-simulated until nothing changes. That's the fixed point.

Notice how symmetric the three entry points are — each builds a MethodVerifier, sets a different initial state, and calls runChecks(). NPA even reuses the exact beforeState values TypeCheck computed, walking them afterward to mark dereference sites as provably non-null (NullPointerAnalysis.java:119).

Adding a fourth analysis = subclass JVMState, define how stack elements merge, register the call in Verifier, and optionally gate it behind a VerifierOptions flag (VerifierOptions.java). The CFG, worklist, subroutines, and exception edges come for free.

The legacy wrinkle: JSR/RET

Older JVMs allowed JSR/RET subroutines — code that pushes a return address and is jumped to multiple times. Naively verifying these breaks, because the locals hold a "return address" that differs per call site. This codebase handles it with a dedicated SubroutineVerifier that runs a second mini-worklist per subroutine and merges its final state back into every RET target (SubroutineVerifier.java:64, :79). The return address itself is an abstract type, TCRAType, tagged with the subroutine's start address (TCState.java:42).

This is the signature of a pre-StackMapTable (pre-Java-6) style verifier. Modern JVMs ditched JSR/RET verification by banning the instructions — a nice example of the JVM simplifying its own spec rather than the verifier.
