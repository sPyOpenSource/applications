Comparing ARM Implementations: JARM vs. lxtreme ARM9

← RISC-V Cycle | SFRs | Next Lesson →

Mission Grounding: To maintain and extend armOS, you must understand the different levels of fidelity in its simulators. Comparing the two ARM implementations reveals the jump from a "simplistic core" to a "full system emulator."

The Relationship

The first surprising discovery is that they are not completely independent. jCPU.arm.CPU (JARM) actually extends nl.lxtreme.arm.CPU.

// src/jCPU/arm/CPU.java:7
public final class CPU extends nl.lxtreme.arm.CPU implements ARMConstants {

JARM uses the lxtreme ARM9 as a base and layers full-system complexity on top of it.

Architectural Comparison

Feature lxtreme ARM9 JARM
Scope Simplistic ARM core Full ARM system emulator
Processor Modes Basic (implied) Full (USER, SYSTEM, HYP, FIQ, IRQ, SVC, ABRT, UND, MON)
Registers Flat GPR array (16 regs) Banked registers (SP, LR, SPSR per mode)
Memory Simple Memory interface PhysicalMemorySpace & VirtualMemorySpace (MMU)
Coprocessors None CP15 (System Control), FPU (VFPv3)
Execution Simple step() Cycle-budgeted execute(budget)

Key Divergences

1. Memory & MMU

While the lxtreme version reads directly from a memory object, JARM implements a virtual memory system. This allows JARM to simulate page tables and translation, essential for running OS kernels.

2. The Control Plane (CP15)

JARM implements CP15.java, which handles system control. This is where the "wisdom" of the CPU resides—controlling the MMU, cache settings, and processor configuration.

3. Execution Fidelity

JARM's execute(int budget) method implements a "debt" system for cycles, allowing for more accurate simulation of instruction timing and interrupt latency compared to the lxtreme's simple step-through approach.
