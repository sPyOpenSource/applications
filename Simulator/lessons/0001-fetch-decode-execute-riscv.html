Tracing a RISC-V Instruction Through the Simulator

Follow one ADD instruction through fetch → decode → execute → writeback

src/jCPU/RiscV/IsaSim.java — the main loop

This lesson traces one RISC-V instruction through the full cycle. By the end you should be able to open IsaSim.java and follow any instruction path without getting lost — you'll know exactly which methods run, how they decode bit fields, and where the results land.

Prerequisites

You know Java. You know what registers and program counters are. No simulator knowledge needed.

The machinery: step()

The heart of every simulator is a loop that runs once per instruction. In IsaSim it lives in step() (line 66). Every instruction — ADD, LW, JAL, ECALL — passes through this exact sequence:

// 1. FETCH — read the 32-bit instruction word from memory at PC
int instr = code.read32(pc);

// 2. DECODE — the low 7 bits tell us the instruction category
int opcode = instr & 0x7f;

// 3. EXECUTE — dispatch to the correct handler
switch (opcode) {
    case LUI_MASK:     loadUpperImmediate(instr);        break;
    case AUIPC_MASK:   addUpperImmediatePC(instr);       break;
    case JAL_MASK:     jumpAndLink(instr);               break;
    case JALR_MASK:    jumpAndLinkRegister(instr);       break;
    case BRANCH_MASK:  offsetPC = branchInstruction(instr); break;
    case LOAD_MASK:    loadInstruction(instr);           break;
    case STORE_MASK:   storeInstruction(instr);          break;
    case OP_IMM_MASK:  immediateInstruction(instr);      break;
    case OP_MASK:      arithmeticInstruction(instr);     break;
    case FENCE_MASK:   /* no-op */                       break;
    case CSR_MASK:     breakProgram = ecallInstruction(); break;
}

// 4. WRITEBACK — advance the PC (unless a branch modified it)
if (!offsetPC) { pc += 4; }
offsetPC = false;
reg[0] = 0;   // x0 is always zero — hardware guarantee

Eleven opcode cases. Nine handler methods. One switch. That's the entire simulator.

Execute

Step 3

The handler at line 516 extracts every field from the instruction word using the same bit-shift pattern:

// ISA Sim.java:516
int rd     = (instr >> 7)  & 0x1F;   // bits 11–7
int rs1    = (instr >> 15) & 0x1F;   // bits 19–15
int rs2    = (instr >> 20) & 0x1F;   // bits 24–20
int funct3 = (instr >> 12) & 0x7;    // bits 14–12
int funct7 = (instr >> 25);          // bits 31–25

Writeback

Step 4

Back in step(), the PC advances past the current instruction:

if (!offsetPC) { pc += 4; }  // pc was 0x100, now 0x104
offsetPC = false;
reg[0] = 0;                    // guarantee x0 stays zero

The simulation counter cc increments. Next call to step() will fetch from 0x104.

Exercise: trace LW

Exercise

The instruction word 0x0042A803 is a LW (load word). Open IsaSim.java and trace it through the four steps:

  1. Which switch case catches it? (What opcode value? What mask constant?)
  2. Which handler method runs?
  3. What are rd, rs1, and the immediate offset?
  4. Which memory address is read, and where does the value go?

Hint: the instruction format is I-type. The handler is at line 375.

Reveal answer
  • 0x0042A803 & 0x7f = 0x03 → LOAD_MASK. Dispatches to loadInstruction(instr).
  • rd = 5 (x5), rs1 = 5 (x5), imm = 4 (no sign extension needed).
  • funct3 = 2 → word load (LW).
  • memAddr = reg[5] + 4. Reads 32 bits via code.read16 (note: there's a bug here — it uses read16 instead of read32 for LW). Writes to reg[5].

Noticed the bug? The simulator has a cut-and-paste error at line 408: LW calls code.read16 instead of code.read32. This means only the low 16 bits of memory are loaded — upper 16 are always zero in practice.

Contrast: ADDI (immediate variant)

ADDI (OP_IMM_MASK = 0x13) follows the same pattern as ADD but reads its second operand from the instruction word instead of a register:

int imm = (instr >> 20);               // bits 31–20
if ((imm >> 11) == 1) imm |= 0xFFFFF000;  // sign-extend from bit 11

switch (funct3) {

The only difference between R-type and I-type is where the second operand comes from. Everything else — the register file access, the ALU operation, the writeback — is identical.

The big picture

Every instruction in this simulator does exactly what you just traced: read a word, decode bits, run a method, update reg[] and pc. No pipeline stages. No hazard detection. No cache. The memory interface is a HashMap<Integer, Byte>.

This is the simplest possible correct simulator — a textbook single-cycle datapath implemented in Java. Understanding this makes the other three simulators (8051, ARM, NASM) much easier to approach: they all share the same fetch→decode→execute pattern, just with different instruction formats and dispatch strategies.
