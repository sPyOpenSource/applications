Performance Tuning the Quadratic Sieve

Reference · bottlenecks ranked by impact

This codebase's SIQS implementation works correctly but has several performance problems that limit it to small inputs (~40 bits). Here are the bottlenecks, ordered from most to least impactful.

1. Single-threaded execution

QuadraticSieve.java:36 private final int threadCount = 1; with a comment "not working on mac". The entire outer loop (execute()) is designed for N threads each sieving independent ranges, but only 1 runs. Fixing this gives an ×N speedup (usually 4–8 on modern hardware).

The fix. The shared collections bSmoothVectors and bigPrimesList are accessed inside synchronized(this) blocks, so the locking already exists. The real issue is probably thread-safety in BigPrimesList.add() which uses HashMap and LinkedList — unsynchronized. Use ConcurrentHashMap or synchronize the method. Then set: 

private final int threadCount = Runtime.getRuntime().availableProcessors();

2. Unbounded y in testSolution

QuadraticSieve.java:236–251 y = y.multiply(savedY) — no .mod(N)! The product grows to n5000 (millions of bits), then y.sqrt() on line 253 must operate on that monster. This alone can make the algorithm hang for minutes.

The fix. Compute y modulo N, the same way x is handled:

y = y.multiply(savedY).mod(N);
// ...
// Instead of y.sqrt(), compute the square root mod N.
// For the quadratic sieve, y should be a perfect square
// (since all exponents are even). Compute it modulo N:
BigInteger z2 = y.add(x).mod(N);
BigInteger gcd = N.gcd(z2);

Actually, the full fix: y is the product of all g(a_i) for the dependency set. Since we know this product is a perfect square (by construction of the dependency), we can track its square root instead:

BigInteger y_root = BigInteger.ONE;
for (...) {
    y_root = y_root.multiply(savedY.sqrt()).mod(N);
    // where savedY is guaranteed square in context
}

3. Array allocation in hot loop

QuadraticSieve.java:146–150 sieve() creates logs, trueLogs, and vectors arrays for every call. Called 10,000 times per batch with sieveVectorBound ≈ 48,611 — that's ~16 GB of array allocations per batch. Massive GC churn.

The fix. Pre-allocate once and reuse:

private double[] logs, trueLogs;
private VectorData[] vectors;

// In constructor or init:
logs = new double[sieveVectorBound];
trueLogs = new double[sieveVectorBound];
vectors = new VectorData[sieveVectorBound];

// In sieve(), just zero them:
Arrays.fill(logs, 0.0);
Arrays.fill(trueLogs, 0.0);
Arrays.fill(vectors, null);

4. Wheel objects allocated every batch

QuadraticSieve.java:138–144 initSieveWheels(position) creates 5000 new Wheel objects every 10,000 iterations. Each Wheel computes the Tonelli–Shanks modular square root in its constructor (line 26). That's 50 million Tonelli–Shanks calls for a full run.

The fix. The wheel's starting offset changes with each polynomial re-initialization (the root shifts). But the prime-specific data (the two solutions from Tonelli–Shanks) is invariant — only the offset relative to the current root changes. Create wheels once and recompute just the offset, not the full square root.

5. Gaussian elimination is O(n³)

BitMatrix.java:37–58 The double loop processes all rows for every column. With B_SMOOTH = 5000, that's 125 billion XOR iterations in the worst case. Each XOR operates on BitSets of length ~5000, so each is ~625 byte operations — ~78 GB of memory operations.

The biggest win here: use sparse elimination. Each relation has a very small number of non-zero entries (typically 5–10 small primes divide g(x)). The matrix is extremely sparse, but the code represents it as dense BitSets. Better approaches:

  • Markowitz pivot selection — pivot on the sparsest rows/columns first to minimize fill-in
  • Block Lanczos method — the standard for large QS post-processing; O(n²) or better for sparse matrices
  • Structured Gaussian elimination — separate the matrix into dense and sparse parts, eliminate the sparse part first

6. baseLog computed incorrectly for small positions

QuadraticSieve.java:133–136 calculateBaseLog(position) returns Math.log(position × (position + double2Root)). For position = 0, this gives log(0) = -Infinity. For small positions, the approximation g(x) ≈ position² + 2·root·position has a significant error because root² − N is not exactly 0.

The fix. Use the exact formula via BigInteger for positions near zero, falling back to the approximation for large positions where it's safe:

private double calculateBaseLog(double position) {
    if (position < SOME_THRESHOLD) {
        BigInteger exact = root.add(BigInteger.valueOf((long)position))
            .pow(2).subtract(N);
        return Math.log(exact.doubleValue());
    }
    return Math.log(position * (position + double2Root));
}

7. tryToSolve called repeatedly

QuadraticSieve.java:88 isReadyToBeSolved() is checked after every sieve call (every position). Once triggered, it calls tryToSolve() which rebuilds the matrix from scratch and re-does the full O(n³) elimination. If the dependency doesn't yield a factor, this happens again with one more row.

The fix. Cache the reduced matrix. When a new relation arrives, use it as an additional constraint on the existing reduced matrix instead of recomputing from scratch. This is a standard technique in QS implementations.

8. Sieve interval is too small

QuadraticSieve.java:51 sieveVectorBound = highestPrime.intValue() — the sieve interval equals the largest factor-base prime (~48,611 for B_SMOOTH = 5000). Standard QS uses an interval of ~10⁵ to ~10⁶ values. A larger interval means more candidates per batch and better cache utilization.

The optimal sieve interval is a trade-off: larger intervals amortize the wheel setup cost but increase memory pressure. A common heuristic is interval = highestPrime × 10–100.
