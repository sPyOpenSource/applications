Lesson 0007: WebSockets Introduction

Mission: HTTP Servers | Lesson: 0007

Learning Goal

Understand what WebSockets are, how they differ from HTTP, and what the codebase currently does (and doesn't do) with WebSocket upgrade requests.

Tangible Win: Explain the WebSocket handshake, why it's needed, and identify the placeholder in this server's parsing logic.

What Are WebSockets?

WebSockets provide full-duplex, bidirectional communication over a single TCP connection. Unlike HTTP's request-response pattern, after establishing a WebSocket connection:

  • Either side can send messages at any time (no need to wait for a request)
  • Communication is persistent - the connection stays open
  • Lower overhead than repeatedly polling via HTTP
  • Great for real-time apps (chat, games, live updates)

How Do WebSockets Work? The Handshake

WebSockets start as an HTTP request - this is called the "upgrade" handshake. The client sends an HTTP GET request with special headers:

GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

The server must respond with a 101 Switching Protocols status if it accepts:

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

After this, the connection is upgraded from HTTP to the WebSocket protocol - both sides can now send frames.

What Does This Codebase Do?

Looking at TCPWebWorker.parse():

case "Content-length:":
    contentsLength = Integer.parseInt(tokenizer.nextToken());
    break;
case "Sec-WebSocket-Key:":
default:
    break;

The server detects the Sec-WebSocket-Key header (it doesn't ignore it entirely - it's in the switch), but it does nothing with it. It just falls to default and continues. It never generates the required Sec-WebSocket-Accept response or performs the protocol upgrade.

In other words: this is a placeholder/detection point, not a working WebSocket implementation.

HTTP vs WebSockets: Key Differences

AspectHTTPWebSockets
CommunicationRequest-Response (unidirectional per request)Full-duplex (bidirectional anytime)
ConnectionShort-lived (often closed after response)Persistent, long-lived
OverheadHeaders sent with each requestOnce after handshake, much lighter frames
Starting PointAlways HTTPHTTP upgrade handshake

Why Detect But Not Implement?

This is common in minimal server implementations - they focus on core HTTP serving and leave WebSocket support as a future extension. To properly implement WebSockets, you'd need to:

  1. Detect the Upgrade: websocket header
  2. Validate Sec-WebSocket-Version (must be 13)
  3. Compute Sec-WebSocket-Accept from Sec-WebSocket-Key + magic GUID
  4. Send 101 Switching Protocols response with correct headers
  5. Switch to WebSocket frame protocol (framing is binary-based, not line-based)

That's significantly more complex than simple HTTP request parsing.
