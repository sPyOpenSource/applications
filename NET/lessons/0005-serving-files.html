Lesson 0005: Serving Files From Filesystem

Mission: HTTP Servers | Lesson: 0005

Learning Goal

Understand how the WebServer can serve actual files from the filesystem via JX's FS interface.

Tangible Win: Trace through how the -fs option works and how readFile() retrieves file contents.

FS Option

From WebServer.java, when started with -fs <FSName>:

case "-fs":
    argc++;
    opt_use_fs = true;
    fsname = args[argc];
    break;

Then later:

if (opt_use_fs) {
    Debug.out.println("Webserver: use filesystem with name " + fsname);
    fs = (FS)LookupHelper.waitUntilPortalAvailable(naming, fsname);
    // create buffer
    MemoryManager memoryManager = (MemoryManager)InitialNaming.getInitialNaming().lookup("MemoryManager");
    buffer = memoryManager.alloc(1024);
    if (opt_dummyfiles) {
        // create index.html and page2.html
    }
}

The server looks up a filesystem service by name from the initial naming context - this is JX's IPC/service mechanism.

Creating Dummy Files

With -dummyfiles, it creates two files programmatically:

createFile(fs, "index.html", 
           "<html>...JX index.html Testseite (FILEXX)...</html>");

createFile(fs, "page2.html", 
           "<html>...</html>");

The helper createFile() does:

private void createFile(FS fs, String name, String contents) throws Exception {
    fs.create(name, InodeImpl.S_IWUSR|InodeImpl.S_IRUGO);
    Node inode = (Node)fs.lookup(name);
    byte[] b = contents.getBytes();
    buffer.copyFromByteArray(b, 0, 0, b.length);
    inode.write(buffer, 0, b.length);
    inode.decUseCount();
}

This shows the JX filesystem API: create file with permissions, look up inode, copy bytes into memory buffer, write to inode, then release reference.

Reading Files in TCPWebWorker

In TCPWebWorker, look at readFile() (around line 120-150 in the full file):

byte[] readFile(String name)  {
    try {
        Node inode = fs.lookup(name);
        int l = inode.getLength();
        Debug.out.println("l: " + l);
        inode.read(buffer1, 0,  l);
        inode.read(buffer2, 1, l);
        byte data[] = new byte[l];
        buffer1.copyToByteArray(data, 0, 0, 512 * 8);
        buffer2.copyToByteArray(data, 512 * 8, 0, l - 512 * 8);
        // debug output...
        return data;
    } catch (Exception ex) {
        Debug.out.println(ex.getMessage());
        return constructErrorHeader().getBytes();
    }
}

Interesting details:

  • Looks up the inode for the filename
  • Gets file length
  • Reads into two memory buffers (buffer1 and buffer2) - possibly for efficiency or due to buffer size constraints
  • Copies from both buffers into a byte array
  • If lookup/read fails (e.g., file not found), returns 404 header as bytes

How it's Used

In the request handling (line ~90-120 in TCPWebWorker):

switch (file) {
    case "stream.exe": // special canned response...
    case "dummy.html": // ...
    case "mini.html":  // ...
    default: {
        String index = "<html>...</html>";
        byte[] data = index.getBytes();//readFile("/" + file);
        ostream.write(constructHeader(file, data.length).getBytes());
        ostream.write(data);
        ...
        break;
    }
}

Look carefully - in the default case, it has byte[] data = index.getBytes();//readFile("/" + file); - the actual filesystem read is commented out in this version! It falls back to returning a hardcoded "index.html" content for any request that hits default. The special cases (stream.exe, dummy.html, mini.html) also return canned responses.

This suggests the filesystem reading code exists but might be experimental/inactive in this specific build. Understanding the API is still valuable.

Key Takeaways

  • The server can be configured to serve from a real filesystem (via JX FS portal)
  • File I/O goes through JX's Memory abstractions and inode operations
  • Error handling: if file can't be read, return 404
  • The actual serving logic might be simplified in the test version
