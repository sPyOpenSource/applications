Lesson 0004: Concurrency Models

Mission: HTTP Servers | Lesson: 0004

Learning Goal

Compare the two concurrency models used by this WebServer: thread-per-connection vs domain-per-connection.

Tangible Win: Understand the difference between threads and JX domains in this context, and when each might be used.

Two Ways to Handle Connections

Looking back at WebServer.java, when a connection arrives:

if (opt_threads)
    startWorkerThread(sock);
else
    startWorkerDomain(sock);

This gives us two different concurrency strategies.

Model 1: Thread-per-Connection

private void startWorkerThread(final Socket sock)  {
    new Thread ("WebWorker"){
        @Override
        public void run() {
            try {
                TCPWebWorker.processRequest(sock, fs);
            } catch(Exception e) {
                //throw new Error();
            }
        }
    }.start();
}

Each connection gets its own Java thread. The thread runs the request handling synchronously until done, then exits. This is a common pattern in many HTTP servers (especially simpler ones).

Pros: Simple, familiar model. Easy to reason about request lifecycle.

Cons: Threads have memory overhead; context switching costs; under high load, thread count grows linearly.

Model 2: Domain-per-Connection (JX Specific)

private void startWorkerDomain(final Socket sock){
    String domainName = "Servlet";
    String mainLib = "init.jll";
    String startClass = "test/net/TCPWebWorker";
    String[] argv = new String[0];
    Object[] portals = new Object [] { sock, fs };
    boolean useChunkedGC = false;
    int codesize = 10000;
    if (useChunkedGC) {
        int HeapInitialSize = 40000;
        int HeapChunkSize = 10000;
        int StartGCSize = 80000;
        Domain domain = DomainStarter.createDomain(domainName, mainLib, startClass, (String)null, HeapInitialSize, HeapChunkSize, StartGCSize, argv, portals);
    } else {
        int HeapSize = 400000;
        Domain domain = DomainStarter.createDomain(domainName, mainLib, startClass, HeapSize, codesize, argv, portals);
    }
}

This creates a JX "Domain" - JX is a Java-based operating system where domains are isolated protection domains (similar conceptually to processes or isolated components). Each connection gets its own domain with its own heap and resources.

Pros: Strong isolation between connections; faults in one domain don't necessarily affect others; resource accounting per domain is possible.

Cons: More heavyweight than threads; domain creation has overhead; JX-specific concept.

Same Worker Logic

Notice both paths call into the same request handling logic:

  • Thread path: calls TCPWebWorker.processRequest(sock, fs)
  • Domain path: creates domain that starts test/net/TCPWebWorker with init(), which receives sock and fs as portals/objects, then calls processRequest()

Compare: in TCPWebWorker, the init() method (called when started as a domain) does:

public static void init(Naming naming, String[] argv, Object[] objs)  throws Exception {
    Debug.out = ...;
    Socket s = (Socket) objs[0];
    processRequest(s, (FS) objs[1]);
    DomainManager domainManager = (DomainManager) naming.lookup("DomainManager");
    domainManager.terminateCaller();	
}

This shows how the domain receives initial objects and cleans up by terminating itself when done.

Real-World Context

In modern web servers:

  • Apache prefork/worker use processes/threads
  • NGINX uses an event loop (asynchronous, non-blocking) - very different model
  • Node.js uses event loop with single thread + async I/O
  • Go uses goroutines (lightweight threads)

This codebase shows two classic models (thread-per-conn, process/domain-per-conn). It's educational to see both sharing the same protocol logic.
