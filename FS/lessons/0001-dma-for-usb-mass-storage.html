Lesson 0001: DMA (Direct Memory Access) for USB Mass Storage

Mission: USB Mass Storage for File System Implementation | Zone: Controller-side DMA for UHCI/EHCI/xHCI

Learning Objectives

  • Explain why DMA is required for USB host controllers
  • Distinguish between virtual, physical, and bus (DMA) addresses
  • Describe the descriptor ring / TD (Transfer Descriptor) lifecycle in UHCI
  • Identify the memory requirements for DMA buffers (alignment, physical contiguity, cache coherency)
  • Spot common DMA bugs in USB host driver code

Why DMA Matters for USB Host

Your USB host controller (UHCI, EHCI, xHCI) is a bus master. It reads and writes system memory without CPU involvement. When you submit a CBW (Command Block Wrapper) or data phase for a SCSI READ(10)/WRITE(10):

CPU builds TD (Transfer Descriptor) in memory
→
CPU writes TD address to controller register
→
Controller DMA-reads TD from RAM
→
Controller DMA-reads/writes data buffer
→
Controller writes completion status back to TD
→
CPU polls/interrupts, reads TD status

Key insight: The controller sees physical addresses. Your C code works with virtual addresses. The memory must be:

  • Physically contiguous (controller DMA can't follow page tables)
  • DMA-accessible (some SoCs restrict DMA to certain RAM regions)
  • Cache-coherent (CPU cache vs. DMA writes must be synchronized)
  • Properly aligned (e.g., 64-byte alignment for UHCI TDs/QHs)

On simple embedded systems without MMU: VA = PA = DMA_ADDR, but alignment and cache rules still apply.

UHCI TD / QH Allocation Pattern

In your UHCI driver, the TD (Transfer Descriptor) and QH (Queue Head) structures must live in DMA-accessible memory. The typical pattern:

// Allocate 32 bytes, 16-byte aligned for TD
td = dma_alloc_coherent(udev->dev, sizeof(struct uhci_td), &td_dma, GFP_KERNEL);
if (!td) return -ENOMEM;

// Build TD in CPU-accessible memory
td->token = cpu_to_le32(...);
td->buffer = cpu_to_le32(data_dma);
td->link = cpu_to_le32(next_td_dma | 0x2); // QH link

// Write to hardware
writel(td_dma, io_regs + FRAME_LIST_BASE);

Common bug: Using kmalloc/malloc instead of dma_alloc_coherent. The buffer may not be physically contiguous or DMA-accessible.

Data Buffer DMA Mapping

For the actual data buffers (CBW, data phase, CSW), you typically use streaming DMA mapping because buffers are reused and may be larger than a page:

// Before submitting to controller
data_dma = dma_map_single(udev->dev, buf, len, DMA_TO_DEVICE);
if (dma_mapping_error(udev->dev, data_dma)) return -EIO;

// Submit to controller (write data_dma into TD)

// After completion
dma_unmap_single(udev->dev, data_dma, len, DMA_TO_DEVICE);

For bidirectional or receive buffers, use DMA_FROM_DEVICE or DMA_BIDIRECTIONAL.

Cache Coherency

If your CPU has a data cache (Cortex-M7, Cortex-A, etc.):

  • Before DMA_TO_DEVICE: Clean cache (write-back) so DMA sees latest data
  • After DMA_FROM_DEVICE: Invalidate cache so CPU reads fresh data from RAM

dma_map_single / dma_unmap_single handle this automatically on Linux. On bare metal:

// Before giving buffer to controller (TX)
SCB_CleanDCache_by_Addr(buf, len);

// After controller writes to buffer (RX)
SCB_InvalidateDCache_by_Addr(buf, len);

Hands-On: Audit Your UHCI Driver

  1. Find where TDs/QHs are allocated. Are they using dma_alloc_coherent (or your platform equivalent)?
  2. Find where data buffers are passed to the controller. Is dma_map_single called before submission and dma_unmap_single after completion?
  3. Check alignment requirements: UHCI TD = 16 bytes, QH = 32 bytes, Frame List = 4KB.
  4. If bare metal: verify cache clean/invalidate around DMA operations.
